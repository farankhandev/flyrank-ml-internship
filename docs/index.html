Machine Learning for Prioritizing Declining Content

```
A practical machine learning study exploring whether content showing declining search performance can be ranked for human review.
```

Abstract

```

This project asks whether machine learning can help identify content items whose search performance is declining. I used historical impressions and query-level signals from the FlyRank internship warehouse and trained a Random Forest classifier to rank potentially declining content. I compared its performance with a Logistic Regression baseline using a client-level holdout split. The Random Forest achieved a ROC-AUC of 0.604, compared with 0.504 for the baseline, and reached 0.880 Precision@50. The results indicate that the model may be useful for deciding which pages should be reviewed first, but they do not show that changing a page will improve its future search performance.

1. Problem

Research Question

Can machine learning help prioritize content items that show signs of declining search performance?

In practice, a team may have many pages to review but limited time and resources. The purpose of this experiment is to see whether a model can produce a useful ranking so that human reviewers can start with the pages most likely to need attention.

The model is therefore intended as a decision-support system. It is not intended to make automatic content decisions or claim that a particular change will improve rankings or traffic.

2. Data

Data Source

The analysis uses the FlyRank internship warehouse full release hosted on Hugging Face.

The main tables used were:

  • dim_clients — client-level metadata and available history dates.
  • dim_content — content-level metadata.
  • fact_content_daily_performance — daily Google Search Console performance data.
  • fact_content_query_90d — content and query-level signals aggregated over the available 90-day window.

Modeling Window

I used a 60-day performance window divided into two 30-day periods. The previous 30 days provided historical signals, while the latest 30 days were used to define the observed decline.

A content item needed at least 100 impressions in the previous 30-day period to be included in the comparison.

This produced 111,247 content items with sufficient performance history. After removing rows with missing values in the selected features, 102,203 items remained for modeling.

No client names, domains, URLs, search queries, or other private identifying information are included in this public analysis.

3. Methodology

Defining Declining Content

A content item was labeled as declining when its impressions during the latest 30-day period were less than 80% of its impressions during the previous 30-day period. In other words, the observed decline was greater than 20%.

Features

The model used five available signals:

  • Previous 30-day impressions (imp_prev30)
  • Visible query count (visible_queries)
  • Rare-query impression share (rare_share)
  • Anonymized-query impression share (anon_share)
  • Top-query impression share (top_query_share)

Models

The main model was a Random Forest Classifier with 200 trees and a fixed random seed of 42.

I used Logistic Regression as the baseline. Both models were trained using the same features and evaluated on the same test split.

Validation

I used GroupShuffleSplit to create a client-level holdout. Approximately 75% of the modeling data was used for training and 25% for testing, while keeping clients separated between the two sets.

The final test set contained 51,702 rows from 13 clients.

Evaluation

Since the practical goal is to decide which content deserves human attention first, I focused on both overall discrimination and the quality of the highest-ranked predictions.

  • ROC-AUC
  • Precision@50
  • Precision@100
  • Precision@500

Leakage Consideration

The decline label was calculated from the latest 30-day impressions compared with the previous 30-day impressions.

One important limitation is that the query-level signals came from the available 90-day query table. Because that period can overlap with the outcome period, some of these features may contain information from the same period used to define the outcome.

For that reason, I treat these results as an experiment in prioritization rather than a production-ready forecasting system.

The Random Forest produced a ROC-AUC of 0.604, compared with 0.504 for Logistic Regression.

The difference was more noticeable among the highest-ranked predictions. At the top 50 items, the Random Forest reached 0.880 Precision@50, meaning that 88% of those items were labeled as declining in the test set.

Overall classification accuracy tells a different story. The Random Forest achieved 61.3% accuracy compared with 65.8% for the Logistic Regression baseline. This is important because the purpose of this experiment is ranking, not simply maximizing classification accuracy.

5. Interpretation & Limitations

Feature Importance

Visible query count 0.117

The feature importance values give a directional view of which signals contributed most to the Random Forest's decisions. They should not be interpreted as causal effects.

Limitations

  • The client-level holdout provides a stronger test of generalization but also makes the prediction problem more difficult.
  • The model predicts the defined declining-impressions label. It does not show that a content refresh will cause performance to improve.
  • The dataset is anonymized, so the results should not be interpreted as evidence about a particular company or website.
  • The available features do not capture every factor that can affect search performance, including changes in search intent, competition, and search-engine behavior.
  • The 90-day query data may overlap with the outcome period, creating a potential temporal leakage concern.
  • Results from this experiment may not generalize equally to future datasets or clients.

Overall, the model should be treated as a decision-support and prioritization tool. A human reviewer should make the final decision about whether a page actually needs to be changed.

6. Ranked Recommendations

1. Start with the highest-ranked pages

When review capacity is limited, begin with the pages at the top of the model's ranking. The Precision@50 result suggests that this smaller group contains a high concentration of content labeled as declining.

2. Look at the underlying search signals

A model score should be a starting point for investigation. Review historical impressions and available query-level signals before deciding whether a page needs attention.

3. Review the content itself

Before making a change, a human reviewer should consider search intent, content quality, freshness, competition, and whether the page still answers the user's needs.

4. Use the ranking when resources are limited

Teams do not always have enough time to review every page. A ranked list can help direct limited review capacity toward a smaller set of higher-priority items.

5. Measure what happens after changes

If a page is refreshed, its search performance should be monitored afterward. The model should not be treated as evidence that a particular refresh will succeed.

Model ranking → Human review → Content decision → Refresh/test → Monitor
```
